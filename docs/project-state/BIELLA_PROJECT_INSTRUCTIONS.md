# Biella Engine — Canonical Project Instructions

## Identity and authority

Biella Engine is a project-neutral universal AI production/execution engine. Mahdi Taghdisi is the final authority for product direction, priorities, architecture, infrastructure use, acceptance, and work policy.

Current owner direction and observed current source/runtime state outrank plans, historical records, provider defaults, and legacy control systems.

## Direct execution

Execute clear requests directly. Inspect only the current state needed by the task. Continue valid existing work instead of restarting it. Diagnose failures from actual output, repair the smallest affected boundary, preserve unrelated valid work, and do not substitute planning, reviews, governance, or ceremony for execution.

Do not claim working, tested, built, rendered, uploaded, deployed, published, or verified results unless the relevant result was actually observed.

## No artificial blockers or hard QA

Biella does not impose universal approval gates, readiness ceremonies, mandatory maker/critic/validator chains, fixed repair counts, arbitrary qualification periods, global reviewer requirements, provider-preparation rituals, phase-completion gates, or forced prompt-stop boundaries.

Real technical dependencies, side effects, resource contention, data compatibility, and the current Project objective may constrain affected work only. Validation is proportional to the actual claim and output contract. Use focused tests, runtime checks, inspection, decode/readback, or other evidence when useful; do not require unrelated QA work.

## Productive legacy reuse

Legacy projects and archives are donor sources, not current Biella authority. Preserve productive software, code, algorithms, technical knowledge, production pipelines, tooling, execution/recovery logic, benchmarks/failure lessons, and useful agent/specialist patterns when technically valid.

Remove or ignore legacy project identity, branding/lore, permanent management hierarchy, blocker/governance rules, mandatory hard-QA stages, arbitrary limits, fixed repair counts, readiness ceremonies, stale paths/hosts/providers/hardware assumptions, fake capability claims, and nonproductive duplicated/drifted material.

Productive donor material may be reused directly when already clean and compatible, or adapted when project coupling must be removed. Do not require quarantine/classification bureaucracy merely to reuse valid code or knowledge. Preserve provenance only where it materially helps attribution, debugging, deduplication, recovery, or integrity.

## Kernel and Project boundaries

The durable kernel remains approximately: Project, Task, Run, Capability, Graph, Node, Artifact, Resource, Event, Knowledge.

Provider, model, tool, GPU, cloud, database, browser, game engine, DCC, renderer, worker, agent, cache, and deployment environment are replaceable implementations/resources unless a universal semantic requirement proves otherwise.

Project-specific requirements, source, assets, brand, visual/content canon, preferences, acceptance, destinations, memory, and outputs stay Project-scoped.

## Execution model

Tasks express desired outcomes and relevant constraints without hardcoding provider/worker topology. Graph revisions are immutable; replanning creates a new revision. Independent Nodes may run concurrently when dependencies, side effects, and Resources permit. Agents/specialists are dynamic execution patterns, not permanent authority hierarchy.

Keep Engine Memory, Project Memory, Run Memory, Historical Evidence, and Cache conceptually separate. Cache is rebuildable acceleration and must not be the only authoritative copy of meaningful work.

## Continuity

New chats, models, Codex sessions, SSH sessions, or workers do not invalidate valid durable work. Recover the smallest affected boundary after failure. Numbered prompts and phases are implementation/navigation units, not mandatory stop or approval gates. Continue dependency-safe productive work according to the current owner objective.
