## Objective
Multiply existing gameplay through versioned Project data instead of adding one-off code. Start with systems that already exist—population, infected/rival actors, encounters, environment state and tuning—so this task does not invent new game design.

## Existing reusable runtime
- Population/encounter: `BiellaPopulation.h/.cpp`, `BiellaPopulationTest.cpp`, D02-02 evidence.
- Existing actor systems: `BiellaInfected.*`, `BiellaRival.*`, `BiellaVehicle.*`, `BiellaDemoPawn.*`.
- Environment state: `BiellaEnvironmentSite.*`, `BiellaEnvironmentTest.cpp`, D02-04 evidence.
- Objective/state: `BiellaDemoObjectiveManager.*`, `BiellaGamesGameState.*`.
- World continuity/identity: `BiellaWorldContinuity.*`.

## Authorized project-local names
Use these names unless current UE/source constraints require a bounded equivalent:
- `BiellaContentDefinitions.h/.cpp` — versioned structured definitions and validation.
- `UBiellaActorVariantData` — Project actor variant definition with stable `FName ContentId` + integer definition version.
- `UBiellaEncounterData` — encounter/population composition definition.
- `UBiellaTuningData` — bounded gameplay tuning definition.
- `UBiellaContentRegistrySubsystem` — Project-scoped runtime lookup/validation owner; no second Engine registry.
- Runtime assets under `Content/Data/` with stable Project IDs.

## First bounded implementation
1. Introduce the versioned data types and registry validation. Malformed, duplicate and unresolved IDs fail explicitly.
2. Move at least two existing actor/population variants and one encounter/tuning set into structured definitions without changing the accepted gameplay semantics.
3. Make `ABiellaPopulationDirector` consume those definitions instead of duplicating variant-specific logic.
4. Prove one runtime system consumes multiple definitions with the same implementation path.
5. Add a negative control for duplicate/missing/incompatible definition references.
6. Preserve exact definition IDs/version/effective values in validation evidence.

## Do not invent
- No item catalog, rarity/currency system, progression tree, monetization, new mission canon or difficulty labels without accepted Project direction.
- Contract 25 applies when inventory/items are actually implemented; do not add inventory merely to satisfy the contract number.
- Contract 53 is conditional and must remain unimplemented if progression is not approved.

## Evidence required
- Editable definitions + runtime consumer source.
- Schema/range/reference validation including negative cases.
- At least two structured variants through one reusable runtime path.
- Stable ID/version compatibility evidence and explicit missing/incompatible behavior.
- Existing population/environment/shared-gameplay regressions remain valid.
